# QCP Web Backend — المرحلة 1 من خطة تحويل Quick Cash Plus لأونلاين

باك إند Node.js/TypeScript مستقل تمامًا، منفصل فعليًا عن مجلد الأوفلاين (`D:\New Project`) — ملوش أي استيراد أو اعتماد عليه. الهدف: نفس منطق أعمال Quick Cash Plus، لكن شغال على سيرفر وبيتكلم عبر HTTP/WebSocket بدل Electron IPC.

## طريقة التشغيل

```bash
npm install
npm run dev
```

بيشتغل افتراضيًا على `http://localhost:4000`، وبيعمل قاعدة بيانات SQLite محلية جديدة في `./data/quick-cash-plus.sqlite` (كل الـ46 migration + بيانات seed زي بالظبط نسخة الأوفلاين). تسجيل الدخول الافتراضي: **admin / admin123**.

```bash
npm run test    # اختبار حقيقي شامل (سيرفر حقيقي + قاعدة بيانات مؤقتة + نداءات fetch فعلية)
```

## إعدادات البيئة (`.env`، انسخ من `.env.example`)

| المتغير | الوصف |
|---|---|
| `QCP_JWT_SECRET` | سر توقيع الـJWT — **إجباري قبل أي استضافة حقيقية**، بدونه بيستخدم سر افتراضي غير آمن مع تحذير في اللوج |
| `QCP_DB_URL` | لو فاضي: SQLite محلي في `./data`. لو محدد: رابط Turso (`libsql://...`) |
| `QCP_DB_AUTH_TOKEN` | توكن Turso (لو محتاج) |
| `PORT` | منفذ السيرفر (افتراضي 4000) |

## إيه اللي اتعمل في المرحلة دي

- **نسخ منطق الأعمال بالكامل تقريبًا** من `src/main/services/` و`src/main/db/migrations/` الأصليين — نفس الكود، بدون تغيير في أغلب الملفات (34 من أصل 37 ملف service).
- **`src/main/handlers.ts`**: نفس جدول "قناة ← دالة" الأصلي (`buildHandlerMap`)، بنفس أسماء القنوات بالظبط — عشان واجهة الويب المستقبلية (المرحلة 3) تقدر تستخدم نفس المنطق اللي الواجهة الحالية بتستخدمه.
- **مصادقة حقيقية لكل مستخدم (JWT)** بدل كود الاتصال المشترك القديم — `POST /api/auth/login` بيرجع توكن، وكل نداء بعد كده لازم `Authorization: Bearer <token>`.
- **نقطة نهاية عامة** `POST /api/rpc/:channel` بتنادي أي قناة من جدول الـhandlers، وبتضيف تلقائيًا "مين نفّذ العملية" للقنوات اللي بتغيّر بيانات (نفس نمط `ACTOR_META_KEY` من preload الأصلي) عشان يتسجل في سجل نشاط المستخدمين.
- **WebSocket** على `/ws?token=...` لبث تحديثات لحظية ("changed") لكل الأجهزة المتصلة بعد أي عملية تغيير — بديل `network/server.ts` الأصلي.
- **قاعدة بيانات**: تدعم SQLite محلي (تطوير) أو Turso (إنتاج) عبر متغيرات بيئة، بدون تغيير في الكود.
- **نسخ احتياطي محلي على السيرفر** (`backup.ts`، مُعدَّل ليشتغل بدون Electron) — يعمل فقط لما القاعدة SQLite محلي؛ لو متصل بـTurso بيرجع رسالة واضحة إن الاسترجاع/النسخ هيتصمم لاحقًا عبر Cloudflare R2.
- اختبار حقيقي شامل (`scripts/self-test.ts`) بيتأكد فعليًا (مش افتراض) من: تهيئة قاعدة البيانات، تسجيل دخول صحيح/غلط، حماية الـendpoints بدون توكن، قراءة بيانات من الـseed، كتابة بيانات فعلية والتأكد إنها اتسجلت، وتسجيل النشاط التلقائي.

## إيه اللي لسه مش موجود (مؤجل لمراحل لاحقة من الخطة)

هذول الملفات/القنوات **مش منسوخة عمدًا** لأنها مرتبطة بـElectron أو محتاجة تصميم مختلف على سيرفر:

| الملف/القناة المستبعدة | السبب | هيتحل في |
|---|---|---|
| `print.ts` (الطباعة الحقيقية) | `webContents.print` + قائمة طابعات النظام Electron-only | مرحلة 4 (QZ Tray) |
| `rawPrinter.ts` | يعتمد على أوامر PowerShell لطابعات ويندوز | مرحلة 4 |
| `catalogImportExport.ts` | `dialog.showOpenDialog/showSaveDialog` (نوافذ نظام) | يحتاج تصميم رفع/تنزيل ملفات عبر المتصفح |
| `attachments.ts` | تخزين محلي + `dialog`/`shell.openPath` | مرحلة تخزين سحابي (Cloudflare R2) |
| `exportReport.ts` (تصدير Excel/PDF) | `BrowserWindow` offscreen لتوليد PDF | يحتاج بديل (مثلاً headless browser على السيرفر) |
| `googleDrive.ts` | `shell.openExternal` لفتح رابط تفويض | قابل للتعديل بسهولة لاحقًا (مش أولوية) |
| `whatsapp.ts` (الفعلي) | بيعتمد على `print.ts` لتوليد PDF الفاتورة + مسار Electron لتخزين جلسة الاتصال | بعد حل الطباعة/PDF على السيرفر |
| `settings:getPrinters` | بديل مؤقت بيرجع `[]` (لا يوجد "طابعات نظام" على سيرفر) | مرحلة 4 |
| الترخيص (`license.ts`) | لسه بنفس منطق بصمة الجهاز — مش مصمم لسيرفر/اشتراك | مرحلة 6 (اشتراك سحابي) |
